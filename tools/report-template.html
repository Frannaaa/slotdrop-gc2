Final Project Report

Giving customers time to book without selling the same seat twice
Implementation status. PR #92 implements the hold APIs and shared availability rule. The countdown, hold-to-booking conversion and integrated phone test remain pending; the public app still runs GC2. This report distinguishes that work from the verified booking and hold evidence.

1. System overview

SlotDrop helps people near Katipunan find discounted workshop seats that a studio has released for sale. Customers browse activities, choose a session and quantity, review a server quote, and save a simulated booking. Studios control the released capacity, booking deadline and standard or buddy price through Owner. The Express API checks availability, calculates money in centavos and stores the booking in PostgreSQL. Confirmation retrieves that saved receipt by ID, while Owner shows bookings and five server-computed business figures.

2. GC2 to Final improvements

Our upgrade is a server-enforced 10-minute seat hold, chosen under step 1, improved by a visible countdown and hold-to-booking persistence.

We chose this because a customer entering their details needs a short, dependable window to finish. The implemented hold changes bookability immediately: other customers cannot claim those seats until the hold expires or is released. It also adds persisted data and server logic, so the reservation survives a restart. The countdown and conversion will complete the visible feedback and saved-booking relation.

GC2 earned 105/100. We retained the session-row lock, refusal of a stale accepted price with a fresh quote, and the original receipt on an identical retry. To address the reported 22-second cold start, we prepared a ten-minute health-ping workflow; its one-off check passed, but recurring operation starts only after merge.

3. Feature explanation and business decision

POST /api/holds accepts a request UUID, session ID and positive quantity. In server/services/holds.js, createHold() locks the session row, checks the server clock and saves the reservation. Reusing the same request returns the same hold; it never starts another ten minutes.

Free seats = released capacity - confirmed seats - active, unexpired holds.
Expiry is the earlier of ten minutes and the booking cutoff. Holding two of four free seats leaves two; expiry restores four if nothing else changes.

The shared slotSelect() query applies that count across discovery, quotes, bookings and Owner. Capacity edits use the same session lock. A hold creates no confirmed booking, commission or studio payout.

Business decision. Keep the 10% commission for a small pilot. One PHP 2,700 seat yields PHP 270 for SlotDrop and PHP 2,430 for the studio before costs. Our four-week model sells 32 of 64 released seats in 28 bookings: PHP 8,532 in fees less PHP 1,400 support and PHP 6,000 outreach/operations leaves PHP 1,132. Break-even is about 27 seats at the same mix. We would expand only if both sides earn a positive contribution after actual costs; these are assumptions, not sales results.

4. Transaction flow

The {{evidenceDate}} rehearsal used actual HTTP routes and a disposable local database. It recorded a two-seat booking for Beginner Mug Handbuilding at Demo Clay Corner, receipt {{receiptId}}. This verifies the existing booking path; it does not prove hold conversion.

  1. UI: The customer journey is Browse, Detail, Selection, Checkout and Confirmation. For the recorded API save, session 1 and quantity 2 were selected.
  2. API: GET /api/pricing/quote?slotId=1&quantity=2 returned the buddy rate of PHP 2,565 per seat: PHP 5,130 total, PHP 513 commission and PHP 4,617 studio payout.
  3. Service: POST /api/bookings supplied fictional guest details, a stable request UUID and the accepted total of 513,000 centavos. createBooking() locked the session, checked seats and cutoff, then recalculated the price.
  4. Database and response: The transaction inserted the booking with price, session-time and fee snapshots, committed, and returned HTTP 201 with its receipt UUID.
  5. UI readback: Confirmation uses GET /api/bookings/:id, which returned the saved record with HTTP 200. Owner independently read the matching booking; an identical POST retry returned HTTP 200 and the same receipt.

Price refusal: SlotDrop returns 409 PRICE_CHANGED with a fresh quote when expectedTotalCentavos differs from the server total, and saves nothing. The brief's generic wrong-total example expects 201; our documented contract preserves the GC2 behavior, then requires explicit acceptance of the fresh quote before a successful save. See docs/refusals.md.

What the implementation taught us

6. Reflection

One bug appeared when Owner moved a booking cutoff earlier: an existing hold could still carry its old, later expiry. We fixed this by shortening affected holds in the same transaction as the cutoff edit. Moving the deadline later does not give customers a fresh reservation window. This made the rule consistent for customers and the studio.

We also learned that a countdown cannot decide whether a seat is available. A closed tab or a paused browser must not leave inventory stuck; the database timestamp and server query release expired holds without waiting for the browser. Local tests alone could not prove that two database connections respect the same lock. The foundation passed 164/164 CI tests at f5ee131, including the real PostgreSQL hold/booking race and container-restart persistence.

The remaining blocker is specific: a quote containing holdId returned HTTP 400, Unsupported quote field: holdId. Next, the server must validate the customer's hold, count its seats once, and convert it atomically with the booking. We will connect the countdown, test both successful and expired checkout on a phone, obtain teammate review and verify the deployed build before tagging final-v1.0.

Commercially, filling a seat is not enough if that buyer would otherwise have paid the studio directly. Our next step is a one-studio pilot that compares total studio sales, extra attendee costs and support spending. The model includes eight displaced direct buyers as a sensitivity, but we still need real observations.
