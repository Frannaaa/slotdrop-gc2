1. System overview

SlotDrop is a workshop-booking sandbox for people near Katipunan and studios with released seats. Customers browse activities, select seats, review a server quote and save a simulated booking. Studios control the allocation, deadline and standard or buddy price. An Express API enforces availability, calculates totals in centavos and stores receipts in PostgreSQL. Confirmation reads the saved booking by ID, while Owner shows the booking and server-computed analytics.

3. Feature explanation and business decision

  1. POST /api/holds validates the retry UUID, session and positive quantity.
  2. createHold() locks the session, reads server time and checks the shared free-seat count.
  3. Expiry is the earlier of ten minutes or the booking cutoff. slotSelect() subtracts only active, unexpired holds. Holding two of four seats leaves two; expiry restores four without a browser timer.
  4. Earlier Owner cutoffs shorten reservations; immediate closure releases them. Later cutoffs do not renew them.
  5. Pending integration: the server validates the matching hold and commits its conversion with the booking in one transaction. The client countdown reports this server state.

Decision with a number. Keep the 10% commission as a pilot hypothesis. A PHP 2,700 standard seat gives PHP 270 to SlotDrop and PHP 2,430 to the studio before costs. The accepted four-week model sells 32 of 64 released seats and leaves PHP 1,132 after assumed support/operating costs; break-even is about 27 seats. Target at least that modeled break-even and expand only if both studio contribution and platform economics are positive. The downside and eight-displaced-direct-buyer sensitivity remain in the business case; these are modeled assumptions, not measured commercial results.

4. Transaction flow

This is a real HTTP save against a disposable local PostgreSQL engine, not a completed browser hold-conversion proof. It uses the existing GC2 booking path. Receipt: e9307380-5724-4bd2-9727-509bb35d8171.

  1. The existing customer journey is Browse, Detail, Selection, Checkout and Confirmation. The captured API rehearsal selects session 1 with two seats.
  2. GET /api/pricing/quote?slotId=1&quantity=2 returns a server buddy total of 513,000 centavos, or PHP 5,130.
  3. POST /api/bookings sends the accepted total, stable request UUID, quantity and fictional guest details. The route calls createBooking().
  4. The service locks the session, rechecks seats and deadline, computes the stored tier/commission and compares the accepted total. A stale amount returns 409 PRICE_CHANGED and saves nothing.
  5. A valid request inserts the receipt snapshots and commits. The response is 201 with a booking UUID; GET /api/bookings/:id reads the same saved record with HTTP 200.
  6. Owner independently reads the matching row. Repeating the same request returns 200 with the original receipt. The controlled run has two bookings, three sold seats and one of four seats left.

The generic Final brief's wrong-total example expects 201. SlotDrop's expectedTotalCentavos is the customer's accepted amount, so a mismatch returns 409 with a fresh quote, preserving the behavior praised in GC2. docs/refusals.md records this difference and the subsequent explicit acceptance/201 readback. The team must retain this explanation in the final evidence.

Technical reflection, architecture and release

6. Reflection

Testing exposed a deadline edge case: changing an Owner cutoff could leave an existing hold with a later expiry. The fix shortens the hold in the same transaction and never renews it when a deadline moves later. Another useful distinction is that a browser countdown does not release stock; the database timestamp and server query decide whether seats are still reserved.

Single-process local tests also do not establish multi-connection locking. The foundation CI passed 164/164 tests, including the real PostgreSQL hold/booking race, as well as production-container restart persistence. Local capture separates the price acknowledgement from the server calculation, and holds from confirmed revenue. Each presenter still needs to supply and defend their own contribution and reflection.

Next, integrate hold-aware quote/save with the countdown, repeat the uninterrupted customer journey and unaided phone test, then refresh the evidence on reviewed main. Commercially, the next step is a small studio pilot to measure incremental sales, direct-channel displacement and support cost before expanding.
